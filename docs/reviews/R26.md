## ✅ Ce qui tient

- **Injection / i18n** : aucun `innerHTML` hors icônes constantes (`utils/dom.ts:41`) ; un libellé `ui.borders.title` = `<img src=x onerror=…>` est rendu en texte et en `aria-label`, jamais en DOM (spec F13). 179 clés fr = 179 clés en, aucune clé orpheline ni dupliquée, les 7 préfixes dynamiques couverts. Zéro `any`, zéro U+00A0, commentaires en français.
- **A11y et états** : Échap ferme chaque dialogue (specs L26 + F11), `mousedown` neutralisé sur tous les déclencheurs, radios dans des `radiogroup` nommés avec `<label for>`, champs numériques libellés (visuellement masqués dans la grille de bordures), `aria-invalid` + `role="alert"` à l'erreur. `indentDecrease` est désactivé à 0 ; `pageLayout` est désactivé (pas masqué) sans `setPageView`/`getLayout` ; `caps` n'existe que si `text.setCaps` est enregistrée.
- **CSS** : les sélecteurs de `page.css` correspondent à la structure commitée du core (`aster--page-view` sur l'hôte, `.aster-content` enfant, en-tête / pied insérés **dans** `.aster-content` autour de `.ProseMirror` → le `position: absolute` a le bon conteneur) ; `box-sizing: border-box` hérité rend `width: 210mm` + padding = A4 exact ; les six variables posées par le core ont un repli ; pas de conflit de spécificité avec `base.css` en écran (égalités résolues par l'ordre d'import, `page.css` après `base.css`).

## 📌 Points à vérifier côté L23 (non jugés ici)

- `page.css:16-17` annonce `--aster-page-margin-header` / `--aster-page-margin-footer` « posées par le core » ; la version commitée de `page-view.ts` (l. 25-30) ne pose que six variables : `headerMm` / `footerMm` du `DocumentLayout` ne sont jamais reflétés (repli 12,7 mm). Soit le core les pose, soit la doc de `page.css` le dit.
- Valeur par défaut des attributs booléens (`keepWithNext`, `pageBreakBefore`) et de `borders` : si ce n'est pas `null`, R26-11 devient majeur.
- Sélection mixte (R26-12) : comportement réel de `tiptap.getAttributes` sur une plage multi-blocs (dernier nœud du type dans la plage).

## 💸 Dette proposée

- **Dialogues non modaux sans piège ni boucle de focus** : Tab après « Appliquer » quitte le panneau et le ferme (`focusout`, spec F11) ; `aria-pressed` posé sur des déclencheurs `aria-haspopup="dialog"` (spec F12 : « Espacement » annoncé « enfoncé »). Modèle hérité de `link-dialog` / `image-dialog`, à traiter dans `dropdown.ts` (boucle Tab dans les panneaux `dialog`, `aria-pressed` réservé aux menus) — hors périmètre L26.
- `createDropdown` : option `shouldRerender` (R26-07) ; `rerender()` ne restitue le focus qu'aux `menuitem`.
- Les classes partagées de dialogue ajoutées par L26 (`.aster-dialog__row`, `__select`, `__input--number`, `__radios`, `__button--secondary`, `.aster-visually-hidden`) vivent dans `page.css` alors que le dialogue d'image (largeur / hauteur côte à côte) en dépend : un intégrateur qui importe « `base.css` + un thème » (chemin documenté dans `aster.css`) perd la mise en page de ces champs. À remonter dans `base.css` (orchestrateur).
- `docs/THEMING.md` ne liste pas encore `--aster-page-*` (prévu « par l'orchestrateur » dans le brief) ; `docs/API_CORE.md:114` annonce 50 identifiants standard, le contrat en a 52.
- `pageLayout` avec `requires: []` est toujours rendu, donc présent mais grisé en permanence sur un core sans vue page ; `WidgetFactory` ne sait pas renvoyer `null`.
