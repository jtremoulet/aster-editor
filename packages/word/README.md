# 📄 @aster-editor/word

> Import et export `.docx`, nettoyage du collage depuis Word et Google Docs pour Aster Editor. Produit du HTML que le schéma ProseMirror accepte tel quel (stylé avec le lecteur OOXML d'Aster, le défaut depuis la 0.6 ; sémantique avec mammoth sur demande), un fichier Word depuis ce même HTML, neuf ou greffé dans le `.docx` d'origine, sections multiples comprises, et un rapport de fidélité qui compare les deux.

## 📦 Installation

```bash
npm install @aster-editor/word
```

Peer dependency : `@aster-editor/core`. Dépendances embarquées : `jszip` (lecture et écriture des paquets `.docx` : prétraitement des variables, lecteur stylé, greffe dans le gabarit, comparateur), `mammoth` (BSD-2, chargé en **import dynamique** uniquement par `importDocx` en mode `semantic`) et `docx` (MIT, chargé en import dynamique par `exportDocx`).

## 📥 `importDocx`

```ts
type DocxInput = File | ArrayBuffer | ArrayBufferView;
function importDocx(input: DocxInput, options?: DocxImportOptions): Promise<DocxImportResult>;
```

Convertit un `.docx` en HTML prêt pour `editor.setHTML` ou `editor.insertHTML`. L'entrée (`DocxInput`) est un `File`, un `ArrayBuffer` ou une vue typée (`Uint8Array`, `Buffer` Node) dont seule la fenêtre `byteOffset`/`byteLength` est lue. Ne lève jamais pour un document Word valide : ce qui n'est pas converti fidèlement remonte dans `warnings` (et, en mode `styled`, dans `lost`). Rejette une erreur nommée `DocxImportError` (message préfixé `invalid-docx:`) si l'entrée n'est pas de l'un de ces types (`null`, chaîne, objet quelconque), n'est pas une archive zip, ne peut pas être lue (`arrayBuffer()` qui rejette), si mammoth ne peut pas la décoder (`semantic`) ou si la partie principale est absente ou illisible (`styled`).

Deux chemins de lecture, choisis par `fidelity` :

- **`'styled'`** (défaut) : le lecteur OOXML d'Aster (`src/docx/reader/`) lit `document.xml`, `styles.xml`, `numbering.xml`, le thème, les en-têtes, pieds et notes avec `jszip` et le `DOMParser` XML, résout les styles (`docDefaults` → thème → `basedOn` → paragraphe → run) et produit le **HTML stylé** du contrat `api/layout.ts` du core : `style` inline normalisés, `data-docx-*`, tableaux et listes complets, sauts de section et tabulations, plus `layout` (sections comprises), `template` et `lost`. Pas de mammoth sur ce chemin.
- **`'semantic'`** : mammoth, HTML sémantique sans mise en forme, comportement des versions 0.4.x, `layout` vide.

> ⚠️ **Migration 0.6 : le défaut est `styled`.** En 0.5, `importDocx(file)` sans option lisait avec mammoth ; depuis la 0.6, il lit avec le lecteur stylé, comme le composant Angular, la démo et le playground le faisaient déjà. Si ton intégration attend le HTML nu de mammoth, passe `importDocx(file, { fidelity: 'semantic' })` : c'est le seul changement à faire. Sinon, vérifie que ta sanitization serveur laisse passer le HTML stylé (`style` de mise en page, `data-docx-*`, `data-section-break`, `data-tab`, voir le [guide d'intégration](../../docs/GUIDE_INTEGRATION.md), chapitres 3 et 9) : c'est ce que ton application reçoit désormais. Les attendus du chemin sémantique sont figés dans `fixtures/docx/expected/semantic/`.

### Ce que l'import produit

Sur le chemin `styled`, en plus des `style` et `data-docx-*` du tableau ci-dessus, la structure est la même qu'en `semantic` (titres, listes imbriquées avec `<p>` dans chaque `li`, `thead` / `th`, notes, puces de variables), à deux différences près : les marques sont imbriquées dans un ordre figé (`<span><strong><em><s><u><sup>`) et les déclarations du `span` dans un ordre figé (`background-color, color, font-family, font-size, letter-spacing, …`), calés sur ce que `getHTML()` du core réémet, pour que `setHTML(getHTML())` rende exactement le HTML de l'import (idempotence stricte, vérifiée sur les fixtures 11-19). Deux nœuds de plus depuis la session 4 : `<hr data-section-break="n">` entre deux blocs de premier niveau là où Word change de section (`n` = numéro de la section qui se termine, 1..k dans l'ordre ; jamais en tête ni deux de suite sans paragraphe entre eux, jamais en fin de corps sans `<p></p>` après : ce sont les invariants que le core impose, le lecteur les respecte pour rester idempotent), et `<span data-tab="" data-stop="56.7pt" data-align="center" data-leader="dot"></span>` pour une tabulation (attributs dans cet ordre, seulement quand le taquet est connu ; `data-align` jamais `left`). Les attendus de ces fixtures (`fixtures/docx/expected/01-06.html`, `08-19.html`, sortie du chemin par défaut) sont figés et régénérés par `ASTER_REGEN=1 npx vitest run src/docx/reader/regen-expected.spec.ts` ; ceux du chemin `semantic` (`expected/semantic/`, 01-03 et 08-10) figent le comportement 0.4.x et ne sont pas régénérés.

Sur le chemin `semantic` (mammoth) :

- **Titres** : `Title`/`Titre` et `Heading 1..6`/`Titre 1..6` (noms localisés et identifiants internes `Heading1`, `Titre1`) → `h1..h6`.
- **Listes** : numérotation native Word (`w:numPr`) → `ul`/`ol` imbriqués ; le texte de chaque `li` est enveloppé dans un `<p>` (schéma Tiptap `listItem = paragraph block*`), les sous-listes orphelines sont rattachées au `li` précédent.
- **Marks** : gras, italique, `Strong`/`Fort` → `strong`, `Emphasis`/`Accentuation` → `em`, souligné → `u`, barré → `s`, surlignage → `mark`, style `Code` → `code`.
- **Citations** : `Quote`, `Intense Quote`, `Citation`, `Citation intense` → `blockquote`, fusionnées quand elles se suivent.
- **Code** : styles `Code`, `HTML Preformatted` → `pre`, lignes consécutives dans un seul bloc.
- **Tables** : `thead` + `th` si Word a marqué la ligne d'en-tête ou si toute la première ligne est en gras, `tbody` pour le reste, `colspan`/`rowspan` conservés, `<p>` unique des cellules déballé.
- **Images** : `src` = URL du hook ou data URL, `alt` toujours présent (vide si absent), `width`/`height` nuls retirés.
- **Notes** : liste `<ol data-footnotes>` en fin de document, appels `[1]` en texte simple, identifiants dans `data-footnote`. Note : le schéma Tiptap ne conserve pas `data-footnote` après `setHTML`.
- **Liens** : `<a href>` natifs mammoth, puis filtrés par la politique de liens du core à l'insertion.
- **Variables** : `<span data-aster-variable="nom" data-label="…">{{nom}}</span>`, voir ci-dessous.
- Paragraphes vides conservés en `<p></p>` (`emptyParagraphs: 'keep'`), supprimés avec `'drop'`.

### Objets non représentables

Mode `styled` seulement. Un objet que l'éditeur ne sait pas représenter est classé (`DocxLostKind` : `textbox`, `shape`, `smartart`, `chart`, `equation`, `comment`, `revision`, `field`, `embedded-object`, `unknown`) et localisé (`DocxLostWhere` : `body`, `header`, `footer`, `footnote`, `endnote`). **Hors du corps**, il reste tel quel dans le gabarit (l'export dans le gabarit ne réécrit pas ces parties). **Dans le corps**, il est remplacé par son texte quand il en a un (`text` : contenu d'une zone de texte, texte inséré d'une révision `w:ins`, résultat affiché d'un champ `DATE`), signalé dans `result.lost` avec un `detail` lisible (nom de la forme, instruction du champ, type d'objet incorporé) et par un avertissement `object-lost`, puis perdu à l'export. Un objet n'est signalé qu'une fois (révisions et commentaires reviennent souvent). Un dessin qui porte une image **et** une zone de texte rend l'image, puis le texte de la zone, signalée comme perdue. Les formes DrawingML de Word 2010+ sont enveloppées dans `mc:AlternateContent` : le lecteur lit le `mc:Choice`, sans quoi tout dessin moderne serait invisible (revue R25). Le texte supprimé d'une révision `w:del` n'est jamais lu.

| `braces`          | `{{nom}}` tapé dans le texte, espaces intérieurs tolérés (`{{ nom }}`), y compris dans un titre, une liste, une cellule, une marque, ou coupé sur deux runs.                                                                                                                                                                                                                                                                                                                                                       | Le nom. Accolades seules et `{{` incomplet restent du texte ; `<pre>` et `<code>` ne sont jamais analysés.                                                                                                                                                                                                                                                          |
| `mergeFields`     | Champs de fusion `MERGEFIELD nom`, forme simple (`w:fldSimple`) ou complexe (`w:fldChar begin … end`, instruction répartie sur plusieurs runs). Un nom, entre guillemets ou non, est gardé tel quel s'il respecte la règle des noms (`"Prénom"` → `Prénom`) ; sinon il est normalisé : minuscules, accents retirés, espaces → `_` (`"Nom complet"` → `nom_complet`).                                                                                                                                               | Le nom, la mise en forme du run et **le résultat affiché** comme valeur connue (`value`), sauf s'il est vide ou n'est que le placeholder `«nom»` / `{{nom}}` : un export `fields` avec `values` se réimporte donc avec ses valeurs. Les autres champs (`HYPERLINK`, `PAGE`, `TOC`, `IF`…) sont intacts.                                                             |
| `contentControls` | Contrôles de contenu `w:sdt` avec `w:tag` (nom) et `w:alias` (libellé) ; sans tag, l'alias normalisé sert de nom. Un contrôle de ligne (dans un paragraphe) devient un run ; un contrôle de bloc fait de paragraphes devient un paragraphe. Sans tag ni alias, ou pour une table des matières, un groupe, une case à cocher, ou un bloc qui contient autre chose que des paragraphes (table, ligne, cellule), le contrôle est laissé tel quel. Liste déroulante, zone de liste et date donnent la valeur affichée. | Le nom, le libellé (`data-label`, `label`) et **la valeur saisie** (`value`), sauf si le contrôle affiche encore son texte de remplissage (`w:showingPlcHdr`). Un tag présent plusieurs fois garde le libellé et la valeur de sa première apparition. Une variable imbriquée dans un contrôle de bloc remplacé n'est pas listée : elle n'est plus dans le document. |

Les champs et contrôles sont réécrits dans le XML du `.docx` **avant** la lecture (mammoth ou lecteur stylé), car mammoth perd les premiers et traverse les seconds ; le lecteur stylé relit les runs `{{nom}}` ainsi produits avec la mise en forme du champ. `result.template` reste le tampon d'origine, pas la version réécrite. Les parties traitées sont localisées par les relations du paquet : le corps désigné par `_rels/.rels` (`word/document.xml` en général), puis ses en-têtes, pieds de page et notes d'après `word/_rels/document.xml.rels` ; sans ce fichier, repli sur les noms usuels (`header1.xml`, `footer1.xml`, `footnotes.xml`, `endnotes.xml`). Une partie sans champ ni contrôle n'est pas parsée. Le prétraitement ne lève jamais : en cas d'échec, le document est importé sans et un avertissement `variables-preprocess-failed` est émis. `result.variables` liste les variables du HTML dans l'ordre d'apparition, puis celles trouvées dans les en-têtes et pieds de page (que mammoth ne rend pas) ; donne-la au core avec `editor.variables.define(result.variables)`.

Les `{{nom}}` tapés dans un en-tête ou un pied de page sont eux aussi remontés dans `result.variables` (sans libellé ni valeur) quand `braces` est actif, avec `pattern` s'il est fourni. Un `{{nom}}` dont les accolades et le nom sont répartis sur plusieurs marques d'un même paragraphe (`<strong>{{</strong>nom}}`, après une correction dans Word) est reconnu : la puce est posée à la place du premier fragment, dans ses marques, et les fragments suivants sont retirés. Il n'est jamais recollé à travers un saut de ligne, une puce ou un bloc.

```ts
const { html, variables } = await importDocx(file, {
  variables: { detect: ['braces', 'contentControls'], pattern: /\[([a-z_]+)\]/g },
});
editor.setHTML(html);
editor.variables.define(variables); // libellés et valeurs connues
```

`pattern` remplace la syntaxe `{{nom}}` du texte libre par un motif dont le **groupe 1 est le nom** (validé par la règle du core : lettres, chiffres, `_`, `.`, `-`). Les runs `{{nom}}` produits par le prétraitement restent reconnus, mais seulement pour les noms qu'il a collectés. Un motif à backtracking exponentiel est à la charge de l'intégrateur. `detect: []` désactive tout.

### Exemple avec `<input type="file">`

```ts
import { createAster } from '@aster-editor/ui';
import { importDocx } from '@aster-editor/word';

const { editor } = createAster(document.querySelector<HTMLElement>('#editor')!);
const input = document.querySelector<HTMLInputElement>('#docx')!;

input.addEventListener('change', async () => {
  const file = input.files?.[0];
  if (!file) return;
  try {
    const { html, warnings } = await importDocx(file, {
      fidelity: 'styled',
      upload: async (image) => {
        const body = new FormData();
        body.append('file', image);
        const response = await fetch('/api/uploads', { method: 'POST', body });
        const { url } = (await response.json()) as { url: string };
        return url;
      },
    });
    editor.setHTML(html);
    for (const warning of warnings) console.warn(`[${warning.code}] ${warning.message}`);
  } catch (error) {
    console.error('Fichier .docx illisible', error);
  }
});
```

Avec un `ArrayBuffer` (fetch, test) : `await importDocx(await response.arrayBuffer())`. Côté Node ou SSR, un `Buffer` passe tel quel : `await importDocx(await readFile('rapport.docx'))`.

## 🧹 `normalizeWordHtml` et `normalizeGoogleDocsHtml`

```ts
function normalizeWordHtml(html: string, options?: WordPasteOptions): string;
function normalizeGoogleDocsHtml(html: string, options?: WordPasteOptions): string;
function isWordHtml(html: string): boolean;
function isGoogleDocsHtml(html: string): boolean;
```

Fonctions **pures** : elles parsent le HTML dans un `Document` neuf, ne touchent jamais au `document` global et renvoient `body.innerHTML` nettoyé. Chaîne vide → chaîne vide. Le fragment réellement copié est isolé entre `<!--StartFragment-->` et `<!--EndFragment-->` quand les marqueurs existent ; si `EndFragment` manque (presse-papier tronqué), la balise ouverte et jamais fermée en fin de chaîne est retirée plutôt que rendue en texte.

Les deux normaliseurs sont aussi une barrière : balises actives supprimées avec leur contenu (`script`, `iframe`, `object`, `embed`, `form`, `template`, `noscript`, `frame`, `frameset`, `svg`, `math`, `meta`, `style`), tout attribut `on*` jeté, liens limités aux schémas `http`, `https`, `mailto`, `tel` (les autres sont déballés en texte), images limitées à `http(s)`, `data`, `blob`, `file` et relatif, valeur de `color` validée avant conservation. Le core applique ensuite sa propre politique de liens et d'images à l'insertion (`file:` et `data:` non-image y sont rejetés). Cette barrière est figée par une suite de tests dédiée (`paste/security.spec.ts`) qui couvre aussi les deux regex quadratiques corrigées en 0.3.0 (`isWordHtml`, `parseListFormats` : un collage de 2 Mo se détecte en moins d'une milliseconde) et les fragments tronqués au milieu d'un vecteur.

### Options (`WordPasteOptions`)

| Champ           | Type                         | Défaut      | Rôle                                                                                                                        |
| --------------- | ---------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------- |
| `keepColors`    | `boolean`                    | `false`     | Conserver `color` explicite. Jamais le noir / `windowtext` par défaut, jamais dans un lien.                                 |
| `keepAlignment` | `boolean`                    | `true`      | Conserver `text-align` (`center`, `right`, `justify` ; `left` est le défaut et tombe).                                      |
| `parse`         | `(html: string) => Document` | `DOMParser` | Parseur injectable pour tests ou environnement sans DOM.                                                                    |
| `variables`     | `boolean \| { pattern? }`    | `true`      | `{{nom}}` collé → puce `<span data-aster-variable>`. `false` désactive, `{ pattern }` remplace la syntaxe (groupe 1 = nom). |

### Les 9 passes Word, dans l'ordre

| #   | Passe                      | Ce qu'elle fait                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `stripConditionalComments` | Avant parsing : jette `<!--[if gte mso 9]>…<![endif]-->` (XML de réglages, VML) et les marqueurs `<![if !supportLists]>`. Après parsing : supprime tous les nœuds commentaire.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 2   | `stripOfficeNamespaces`    | Supprime avec leur contenu `<xml>`, `<style>`, `<script>`, `<meta>`, `<link>`, `<title>`, `<head>` et les balises actives `<template>`, `<iframe>`, `<object>`, `<embed>`, `<form>`, `<noscript>`, `<frame>`, `<frameset>`, `<svg>`, `<math>` ; déballe les balises préfixées `<o:p>`, `<w:*>`, `<v:*>`, `<m:*>` en gardant leur texte.                                                                                                                                                                                                                                                                                                                                                           |
| 3   | `rebuildLists`             | Lit `mso-list:lX levelN lfoM` sur les paragraphes et, dans le `<style>`, `@list lX:levelN { mso-level-number-format; mso-level-start-at }` puis les overrides d'instance `@list lX:levelN lfoM {…}` qui priment ; reconstruit `<ul>`/`<ol>` imbriqués, pose `type` (`a`, `A`, `i`, `I`) et `start` (lu dans le marqueur, sinon `mso-level-start-at`). Sans feuille de style, décide via le texte du marqueur : `1.`, `1.1.` décimal ; `c.`, `d.`, `l.`, `m.` isolés alpha ; `i.`, `v.`, `x.` isolés romains sauf si le marqueur suivant est `j.`, `w.`, `y.` ; deux lettres romaines ou plus (`ii.`, `iv.`) romain. Chaque instance `lfo` est une liste distincte.                                |
| 4   | `normalizeHeadings`        | `MsoTitle` → `h1`, `MsoHeading1..6` → `h1..h6` (plafonné à 6), `MsoQuote` / `MsoIntenseQuote` → `blockquote` fusionnés.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| 5   | `cleanInlineStyles`        | Jette `mso-*`, polices, tailles, interlignes, marges, fonds, `class`, `lang` ; traduit `font-weight:bold` → `strong`, `font-style:italic` → `em`, `underline` → `u`, `line-through` → `s`, `vertical-align` → `sub`/`sup`, `mso-highlight` → `mark` ; renomme `b`/`i`/`strike`/`del`/`ins` ; ne garde que `href`/`title`/`target`/`rel` sur `a`, `src`/`alt`/`title`/`width`/`height` sur `img`, `start`/`type` sur `ol` ; déballe les `<a>` sans `href` ou d'un schéma autre que `http`, `https`, `mailto`, `tel`, supprime les `<img>` à `src` actif ; avec `keepColors`, ne garde `color` que si la valeur est un hexa, un nom CSS ou un `rgb()`/`hsl()` ; déballe les `span` et `font` vides. |
| 6   | `normalizeTables`          | Retire `border`, `cellspacing`, `width`, `valign`, styles ; garde `colspan`/`rowspan` > 1 ; première ligne toute en gras → `<thead><th>` (le `mso-yfti-firstrow:yes` de Word n'est pas un indice : il marque la première ligne de toute table) ; déballe le `<p>` unique des cellules sauf s'il porte encore un attribut (alignement). Une table à une ligne n'a pas d'en-tête.                                                                                                                                                                                                                                                                                                                   |
| 7   | `collapseEmptyParagraphs`  | Supprime `<p>&nbsp;</p>`, `<p><br></p>`, les `<br>` en fin de bloc et les `<br>` orphelins. Garde un `<p></p>` si tout se vide.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| 8   | `normalizeWhitespace`      | `&nbsp;` entre mots → espace, suites d'espaces réduites, trim en début et fin de bloc (seulement pour un texte réellement en bord de bloc : l'espace entre un texte et une image inline reste), espaces de bord sortis des marks (`<em>a</em><u> b</u>` → `<em>a</em> <u>b</u>`), blancs d'indentation entre blocs supprimés. `<pre>` intact.                                                                                                                                                                                                                                                                                                                                                     |
| 9   | `wrapVariables`            | `{{nom}}` dans les nœuds texte (hors `<pre>`, `<code>`) → `<span data-aster-variable="nom">{{nom}}</span>`, après fusion des textes adjacents pour recoller un `{{` coupé sur deux spans. Espaces intérieurs tolérés, accolades seules ignorées, nom validé par la règle du core. Option `variables` (`false`, ou `{ pattern }`).                                                                                                                                                                                                                                                                                                                                                                 |

Le pipeline Google Docs est plus court : passes 1, 2, puis déballage du `<b style="font-weight:normal" id="docs-internal-guid-…">`, réimbrication des sous-listes (`<ul><li>a</li><ul>…</ul></ul>` → dans le `li`), remontée du `list-style-type` des `<li>` (`lower-alpha`, `upper-alpha`, `lower-roman`, `upper-roman`) en attribut `type` du `<ol>`, passe 5, déballage du `<div>` nu que Google pose autour de chaque table, puis passes 6 à 9.

```ts
import { isWordHtml, normalizeWordHtml } from '@aster-editor/word';

const html = event.clipboardData?.getData('text/html') ?? '';
if (isWordHtml(html)) {
  const clean = normalizeWordHtml(html, { keepColors: true });
  editor.insertHTML(clean);
}
```

Détection : `isWordHtml` cherche `urn:schemas-microsoft-com:office:word`, `class="Mso…"`, `mso-*:`, `<o:p>` ou le `ProgId Word.Document` ; `isGoogleDocsHtml` cherche `id="docs-internal-guid-`. Travail sur la chaîne, sans parser.

## 🔌 `wordPasteTransformer`

```ts
function wordPasteTransformer(options?: WordPasteOptions): PasteTransformer;
```

Fabrique le transformateur à passer dans `pasteTransformers` : détecte Word puis Google Docs, applique le normaliseur adapté, laisse tout autre HTML intact. En cas d'erreur interne, journalise un `console.warn` et rend le HTML d'origine : un collage ne casse jamais l'éditeur.

```ts
import { createEditor } from '@aster-editor/core';
import { wordPasteTransformer } from '@aster-editor/word';

const editor = createEditor({
  element,
  pasteTransformers: [wordPasteTransformer({ keepAlignment: false })],
});
```

Avec `createAster` de `@aster-editor/ui`, même option : `createAster(host, { pasteTransformers: [wordPasteTransformer()] })`.

## 📤 Export .docx

```ts
function exportDocx(input: string | AsterDocument, options?: DocxExportOptions): Promise<Blob>;
function downloadDocx(blob: Blob, filename?: string): void;
function jsonToHtml(document: AsterDocument): string;
```

Convertit le HTML d'Aster (`editor.getHTML()`) ou un document JSON ProseMirror (`editor.getJSON()`) en fichier Word. Rend un `Blob` de type `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, prêt pour `downloadDocx` ou un upload. Ne lève jamais pour du HTML valide : ce qui n'a pas d'équivalent Word remonte via `options.onWarning`. La lib `docx` (MIT, ~1,3 MB non minifié) est chargée en **import dynamique** au premier appel, comme mammoth pour l'import : elle n'entre dans le bundle initial que si ton bundler ne fait pas de code-splitting.

Le JSON passe par `jsonToHtml`, sérialiseur minimal limité au schéma d'Aster (StarterKit, tables, images, alignement, surlignage, indice/exposant, `textStyle`, tâches). Pour un schéma étendu par tes propres extensions, donne plutôt `editor.getHTML()` à `exportDocx`.

En mode `semantic`, les alignements, couleurs et polices ne survivent pas à l'import (mammoth les jette volontairement) ; en mode `styled`, tout le contrat de mise en page survit à l'aller-retour export neuf → import (`export/layout.spec.ts`).

Le texte est assaini avant d'entrer dans le XML : les caractères de contrôle que XML 1.0 interdit (U+0000-U+0008, U+000B, U+000C, U+000E-U+001F) et les non-caractères U+FFFE/U+FFFF sont retirés des runs, des `alt`/`title` d'image, des `href` et des propriétés `title`/`creator`. Sans ça, Word refuse d'ouvrir le fichier. Tabulations, sauts de ligne, espaces insécables et Unicode étendu sont conservés tels quels ; seuls les blancs HTML (espace, tabulation, LF, CR, FF) sont réduits selon les règles du HTML.

### Variables à l'export

Convention du core : `<span data-aster-variable="nom" data-label="Nom">{{nom}}</span>`. Un `{{nom}}` en texte brut (sans span) est aussi reconnu en modes `fields` et `resolve`, via `variables.pattern` (groupe 1 = nom ; par défaut `{{nom}}`, nom en lettres, chiffres, `_`, `.`, `-`, blancs tolérés). Les blocs `<pre>` et marques `<code>` ne sont jamais analysés. Un motif personnalisé est recompilé avec `g` (et sans `y`) puis appliqué tel quel à tout le texte du document : sa complexité n'est pas bornée, un motif pathologique (ReDoS) relève de l'intégrateur.

Une valeur est de la **donnée**, pas du HTML : ses blancs sont écrits tels quels et ses sauts de ligne (`\n`, `\r\n`) deviennent des `<w:br/>` en `resolve`, des espaces dans le résultat d'un champ en `fields`. Une valeur non chaîne (`42`, `true`) est convertie par `String()` ; `null`/`undefined` valent « sans valeur ».

| `variables.mode`        | Rendu dans Word                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `placeholders` (défaut) | Texte `{{nom}}` tel quel, marques conservées.                                                                                                                                                                                                                                                                                                                       |
| `resolve`               | Valeur de `values[nom]`, marques du span et de son contexte conservées. Sans valeur : `{{nom}}` + avertissement `variable-unresolved`.                                                                                                                                                                                                                              |
| `fields`                | Champ de fusion `w:fldSimple w:instr=" MERGEFIELD nom "`. Résultat du champ : la valeur connue, sinon `«nom»`. Un nom avec blanc, guillemet ou backslash est cité (`MERGEFIELD "Nom du client"`, `\` et `"` échappés). `importDocx` relit ces champs en variables. `fldSimple` ne porte pas de propriétés de run : les marques du span ne survivent pas en ce mode. |

```ts
await exportDocx(editor.getHTML(), {
  variables: { mode: 'fields', values: { nom: 'ACME' } },
});
```

### En-têtes, pieds de page, table des matières, notes

- **En-tête / pied** : `header: 'Confidentiel'` ou `{ html: '<strong>Nebula</strong> {{client}}', align: 'right' }`. Le HTML passe par le convertisseur du corps (marques, liens, variables dans les trois modes, plusieurs paragraphes) ; `align` s'applique aux paragraphes sans `text-align` propre. `footer.pageNumbers: 'x-of-y'` ajoute un dernier paragraphe `PAGE / NUMPAGES`, centré sans `align`, sinon aligné comme le reste (`'left'` compris). Une option vide n'émet rien. Word refuse les appels de note hors du corps : un `<sup data-footnote-ref>` ou `<sup>[n]</sup>` dans `header.html`/`footer.html` reste un exposant `[n]` (avertissement `footnote-not-allowed`), et une liste `<ol data-footnotes>` placée dans `header.html`/`footer.html` n'est pas collectée comme notes — elle est rendue comme une liste ordinaire de l'en-tête ou du pied. Seule la liste du corps alimente `footnotes.xml`.
- **Table des matières** : `toc: { title: 'Sommaire', levels: 2 }` insère le titre (style `TOC Heading`, hors des niveaux de titre) et le champ `TOC \h \o "1-2"`, **prérempli** avec les titres du document (entrées cliquables). Les numéros de page sont calculés par Word : le fichier porte `w:updateFields`, Word demande à l'ouverture « Ce document contient des champs… mettre à jour ? » — répondre Oui. LibreOffice met le champ à jour sans demander.
- **Notes de bas de page** : le format produit par `importDocx` (`<sup>[1]</sup>` + `<ol data-footnotes><li data-footnote="footnote-1">`) redevient de vraies notes Word ; `<sup data-footnote-ref="1">` est aussi accepté, et un `<li>` sans `data-footnote` est désigné par sa position (ou la première clé libre si cette position est déjà prise par un `data-footnote` explicite). Word n'accepte qu'un appel par note et aucun appel dans une note : un second `<sup>` vers la même note, ou un appel depuis le texte d'une note, reste un exposant `[n]` avec avertissement `footnote-duplicate` / `footnote-not-allowed` ; une note déclarée deux fois sous la même clé garde la première. L'aller-retour `exportDocx` → `importDocx` restitue le même HTML.
- **Numérotation des titres** : `numberedHeadings: true` lie une numérotation à `Heading 1..3` (`w:pStyle` dans `numbering.xml`, `w:numPr` dans le style) : Word numérote les titres existants et ceux ajoutés ensuite, la table des matières reprend les numéros. `format: 'legal'` supprime le point final (`1`, `1.1`).
- **Mise en page** : `page: { orientation: 'landscape', margins: { top: 20, bottom: 20, left: 15, right: 15 } }`. Les images et les tables sont plafonnées à la largeur utile résultante. Une marge négative reprend le défaut, et deux marges opposées dont la somme ne laisse pas 1 cm de zone utile sont réduites à proportion ; les deux cas remontent `page-margins-clamped`.
- **`layout`** (session 3) : un `DocumentLayout` du core, en général celui de l'import, pilote l'export neuf d'un coup : `page` (format nommé ou libre en mm, orientation, marges, distances d'en-tête et de pied), `columns`, `defaultFont`, `lang`, `headers` / `footers` des trois types (`default`, `first`, `even` : `w:titlePg` et `w:evenAndOddHeaders` posés), `titlePage`. Les options historiques (`page`, `header`, `footer`, `defaultFont`, `lang`) priment champ par champ quand les deux sont données : `options.header` remplace `layout.headers.default`, `first` vient toujours du `layout`. Un aller-retour export neuf → import stylé rend le même `layout`.
- **Sections** (session 4, `export/sections.ts`) : un corps à `k` sauts `<hr data-section-break>` de premier niveau donne `k + 1` sections Word. Le segment `n` reçoit `layout.sections[n - 1]` (`page`, `columns`, `start` → `w:type` `continuous` / `evenPage` / `oddPage`, `titlePage`, `headers` / `footers`) ; le dernier segment reçoit `layout.sections[dernier]` seulement si la liste compte autant d'entrées que de segments, sinon les champs de premier niveau du `layout` (comportement 0.5). Les options `page` / `pageSize` / `header` / `footer` gardent leur portée « tout le document » : elles complètent chaque section qui ne déclare pas la sienne et priment sur la dernière (R43-03). Un segment vide reçoit un paragraphe porteur ; un segment qui finit par un tableau aussi (Word l'exige). Un aller-retour export neuf → import stylé rend trois sections pour trois sections (`export/sections.spec.ts`, `sections-options.spec.ts`).

### Export dans le gabarit

```ts
const imported = await importDocx(file, { fidelity: 'styled' });
editor.setHTML(imported.html);
// … édition …
const blob = await exportDocx(editor.getHTML(), {
  template: imported.template,
  layout: imported.layout,
  variables: { mode: 'fields' },
});
```

Avec `template`, `exportDocx` ne construit pas un document neuf : il **ouvre le gabarit** et y **greffe** le corps produit par la chaîne d'export (`src/docx/writer/`). Tout ce qui n'est pas le corps ressort **identique à l'octet** : `styles.xml`, `numbering.xml`, `theme/*`, `fontTable.xml`, `settings.xml`, `docProps/*`, en-têtes, pieds, médias existants et tous les `w:sectPr` (format, marges, colonnes, références d'en-têtes, de chaque section et le final). Un gabarit relu puis réécrit sans toucher une partie ne la recompresse même pas (`xml-io.ts` ne marque modifiées que les parties écrites). Un aller-retour sans modification des fixtures 11, 13 et 16 rend un `document.xml` lui aussi identique à l'octet ; 12, 14, 15, 17-19 ne diffèrent que par des équivalences (`w:jc left` omis, ordre des attributs).

Ce que la greffe fait, module par module (`writer/`) :

Quand un `.docx` vient d'un import, `exportDocx` ne pose **jamais** d'exception à cause du gabarit : tout repli passe par `onWarning`.

## 📏 `compareDocx` et le rapport de fidélité

```ts
function compareDocx(
  original: DocxInput,
  result: DocxInput,
  options?: CompareDocxOptions,
): Promise<FidelityReport>;
```

Compare deux `.docx` **propriété par propriété**, pas à l'octet : les parties annexes du paquet sont comparées à l'octet (`identicalParts` / `changedParts`, tout sauf `word/document.xml`, `docProps/core.xml` et les `.rels` du corps par défaut, `binaryParts` pour choisir), les blocs des deux corps sont alignés (préfixe et suffixe communs, LCS borné, puis ancrage par clés uniques façon patience diff sur les longues séquences : un bloc déplacé ne décale pas tout le reste) et leurs propriétés **résolues** (styles, `docDefaults`, thème de chaque document) comparées, puis les sections avec leurs en-têtes et pieds. Chaque occurrence compte : conservée si les deux valeurs canoniques sont égales, perdue sinon, cinq exemples par propriété. Décisions figées : une valeur **ajoutée** par le résultat compte comme perdue (strict, pour que les régressions se voient) ; les défauts de Word (gauche, portrait, une colonne, espacement nul, interligne simple) valent « absent » ; les `w:rsid*` sont ignorés (`ignoreRevisionIds`, vrai par défaut). Le comparateur mesure **ce que Word rend**, pas la forme XML : bordures de cellule effectives (style de tableau, **formats conditionnels compris** depuis L46, résolus par cellule selon `w:tblLook` comme le lecteur, `0x04A0` quand l'élément manque → `w:tblBorders` selon la position dans la grille → `w:tcBorders`, `nil` efface), sans l'espace texte-trait `w:space` sur les bordures de tableau et de cellule (Word ne l'applique pas, L45a), saut de page comme frontière de bloc, champs de fusion par nom et résultat (un `{{nom}}` en clair vaut un champ de même nom), largeurs à ±0,5 pt, images par nombre et dimensions (±1 px), taquets d'un paragraphe tabulé par position et alignement (`paragraph.tabs`), alignement du tableau (`table.align`) et drapeaux `w:tblLook` effectifs quand le style définit des formats conditionnels (`table.conditional`) ; un fond ou un gras posé en direct sur la cellule vaut le même venu du style. L'habillage des images, les points de suite des taquets, le `w:pPr` des formats conditionnels, les commentaires, signets et `w:lastRenderedPageBreak` ne sont pas comparés (`report.notes` le rappelle). Les sections sont comparées une à une (`section`, `header-footer` : format, marges, colonnes, type, en-têtes et pieds effectifs).

`FidelityReport` : `score` (moyenne pondérée des taux conservé / total par groupe ; poids `text` 3, `paragraph-style` 2, `paragraph-format` 2, `run-format` 2, `list` 1, `table` 2, `image` 1, `note` 1, `header-footer` 2, `section` 2, `package-part` 2 ; un groupe sans occurrence ne compte pas), `properties` (`{ name, group, total, kept, lost, examples: { where, expected, actual }[] }`), `identicalParts`, `changedParts` (`{ path, summary }`, `summary` vaut `ajoutée` pour une partie nouvelle), `lost` (objets non représentables signalés par l'import stylé des deux documents), `notes`. Un document comparé à lui-même vaut 1.

#### Limites connues de l'export

- **Liste dans une citation** : exportée fidèlement (paragraphes de style `Quote` numérotés, lisibles dans Word), mais **dégradée à la réimportation en mode `semantic`** par mammoth, qui suit le style et jette la numérotation : `<blockquote><ul><li>a</li></ul></blockquote>` revient en `<blockquote><p>a</p></blockquote>`. Le chemin `styled` (défaut) la relit telle quelle.
- **`li` multi-paragraphes avec sous-liste** : export Word standard (seul le premier paragraphe porte la puce, les suivants sont indentés). À la **réimportation en mode `semantic`**, mammoth sort les paragraphes non numérotés de la liste et la coupe en listes sœurs : `<ul><li><p>a</p><p>b</p><ul><li><p>c</p></li></ul></li></ul>` revient en `<ul><li><p>a</p></li></ul><p>b</p><ul><li><p></p><ul><li><p>c</p></li></ul></li></ul>`.
- **`<ol start>`** : écrit dans `numbering.xml` (`w:start` et `startOverride`), honoré par Word et relu par le chemin `styled`, mais **non relu par mammoth** (`semantic`) : l'aller-retour sémantique rend un `<ol>` sans `start`.
- **Bloc dans un inline** (`<span><div>…</div></span>`) : le bloc ne peut plus devenir un paragraphe, son texte est isolé par des sauts de ligne dans le paragraphe courant.
- **Champs de fusion sans marques** : en mode `fields`, `w:fldSimple` n'accepte pas de propriétés de run, un `<strong><span data-aster-variable>` perd son gras. Utilise `resolve` quand la mise en forme compte plus que le champ.
- **Table des matières à mettre à jour** : les numéros de page ne sont jamais écrits par l'export, Word les calcule à l'ouverture après confirmation.
- **Numérotation des titres non relue** : les numéros automatiques (`numberedHeadings`) sont un champ de numérotation, pas du texte ; aucun des deux chemins ne les rend dans le HTML, un aller-retour rend des titres sans `1.` (le gabarit, lui, conserve la numérotation).
- **En-têtes, pieds et notes à la réimportation** : en mode `semantic`, mammoth ignore les en-têtes et pieds de page ; en `styled`, ils reviennent dans `layout.headers` / `footers` (et par section), pas dans le corps. Les notes reviennent via `data-footnotes` sur les deux chemins.
- **Largeurs de colonnes** : le `colwidth` Tiptap est en pixels d'écran (1 px = 15 twips) ; une table plus large que la zone de texte est réduite proportionnellement. Les largeurs en `%` sont ignorées.
- **Tables de plus de 63 colonnes** : les fusions sont bornées à 63, mais une table qui compte réellement plus de 63 colonnes est exportée telle quelle (aucune colonne n'est jetée) ; Word, limité à 63, peut la réparer à l'ouverture.

Les trois premières dégradations (chemin `semantic`) sont figées par des tests d'aller-retour (`export/lists.spec.ts`, cas X-3, M-1 et M-2 des revues) et la quatrième par `export/html-to-docx.spec.ts` (M-5), pour qu'une régression soit visible.

### Exemple avec un bouton

```ts
import { createAster } from '@aster-editor/ui';
import { downloadDocx, exportDocx } from '@aster-editor/word';

const { editor } = createAster(document.querySelector<HTMLElement>('#editor')!);

document.querySelector('#export')?.addEventListener('click', async () => {
  const blob = await exportDocx(editor.getHTML(), {
    title: 'Compte rendu',
    creator: 'Aster',
    fetchImage: async (src) => {
      const response = await fetch(src);
      return response.ok ? response.arrayBuffer() : null;
    },
    onWarning: (warning) => console.warn(`[${warning.code}] ${warning.message}`),
  });
  downloadDocx(blob, 'compte-rendu');
});
```

`downloadDocx` crée un `<a download rel="noopener">` éphémère et révoque l'URL objet juste après le clic ; le nom reçoit `.docx` s'il ne l'a pas et ses caractères interdits (`\ / : * ? " < > |`) sont remplacés par `-`, `document.docx` par défaut. À appeler depuis un gestionnaire d'événement utilisateur. Hors navigateur (SSR, Node), la fonction lève : envoie plutôt les octets, `Buffer.from(await blob.arrayBuffer())`.

Un `exportDocx` sans `DOMParser` global ni `options.parse` lève aussi une erreur explicite, et une entrée qui n'est ni chaîne ni objet est refusée avant tout chargement de `docx`.

## ⚠️ Limites connues

Mode `styled` (défaut) et export dans le gabarit (sessions 3 et 4) :

- **Styles conditionnels de tableau** (`w:tblStylePr` : première ligne, première colonne, bandes) : résolus en propriétés directes de cellule à l'import (bordures, fond, gras et couleur des runs), **non réécrits comme style** à l'export : `w:tblLook` et `w:tblStylePr` ne sont pas régénérés, le tableau reste visuellement identique mais Word lui applique son masque par défaut (`0x04A0`, `firstColumn` activée) et sa mise en forme ne suit plus le style (fixture 19 : 0,998, `table.conditional` ×1 ; proposition de contrat `TableLayoutAttrs.look`). Le `w:pPr` d'un format conditionnel (alignement, espacement) n'est pas lu.
- **Taquets de tabulation** : la n-ième tabulation d'un paragraphe prend le n-ième taquet, sans mesure du texte : faux après un `w:br` (Word repart de la marge) ; `w:defaultTabStop` (`settings.xml`) n'est pas lu, une tabulation sans taquet est un espace élastique de 2 em à l'écran. Alignement et points de suite sont conservés dans le `.docx` (`w:val`, `w:leader`), mais l'écran n'aligne pas le texte sur le taquet (`center`, `right`, `decimal` rendus comme `left`).
- **`w:space` d'une bordure `between`** : lu, mais `data-border-between` n'a pas de `padding` : perdu à `setHTML(getHTML())` et à l'export (R41-09, décision de contrat en attente). Sur les bordures de cellule, `w:space` est écrit 1 pt (haut / bas) ou 4 pt (gauche / droite) quelle que soit la valeur d'origine, et Word ne l'applique pas (non comparé).
- **Style de lien forcé** : un lien ressort avec `w:rStyle Hyperlink`, réconcilié sur le style localisé du gabarit (`Lienhypertexte`, souligné) même si l'original ne l'appliquait pas : seule perte restante du document client (R43-09, dette).
- **Habillage des images** : une image ancrée (flottante, derrière le texte) devient inline, alignée par `data-align` ; sa position exacte, son rognage et ses effets sont perdus.
- **Pagination** : rien dans ce paquet ne calcule de pages. La vue page du core et sa pagination approximative sont un confort d'écran ; le `.docx` produit laisse Word paginer.
- **Espaces finaux et runs vides** : un run réduit à un espace peut être retiré avec son espace à l'export (document client, `paragraph.text` ×2).
- **Sections** : numérotation de page par section (`w:pgNumType`), bordures de page et filigranes ne sont pas lus (conservés par le gabarit quand le `w:sectPr` y est greffé, perdus pour une section ajoutée dans l'éditeur) ; une section sans bloc ressort comme une page blanche ; l'en-tête `first` d'une section du gabarit dont le saut a été supprimé n'est plus hérité (comme Word).
- **Objets non représentables** dans le corps : remplacés par leur texte et perdus (voir plus haut). Dans les en-têtes et pieds, intacts tant qu'un `layout` ne régénère pas la partie.
- **En-têtes et pieds régénérés** depuis `layout` passent par l'export neuf : ils perdent ce que l'export neuf ne sait pas écrire (tableaux complexes, images ancrées, champs autres que `PAGE` / `NUMPAGES` / fusion).
- **`{{nom}}` d'un en-tête du gabarit coupé sur deux runs** : non résolu en mode `resolve`.
- **Gabarit volumineux** : une partie principale de plus de 16 Mo est refusée (`template-invalid`, export neuf) plutôt que parsée.

Mode `semantic` (mammoth, sur demande depuis la 0.6) et collage :

- **Pas de fidélité de mise en page** : colonnes, en-têtes et pieds de page, sauts de page, sections, tabulations, polices exactes, tailles et interlignes sont volontairement jetés par mammoth. L'objectif est de préserver l'intention (structure, emphase), pas le rendu. Les en-têtes et pieds ne sont lus que pour y collecter des variables (`result.variables`). Reste sur `styled` (le défaut) pour tout conserver.
- **Images collées depuis Word sous Windows** : le presse-papier référence des fichiers locaux (`file:///C:/Users/…/clip_image001.png`). Le navigateur ne peut pas les lire, la politique de liens du core rejette `file:` et l'image est perdue. Passe par l'import `.docx` ou par un glisser-déposer du fichier image.
- **Formes, zones de texte, SmartArt, équations** : contenu VML/DrawingML non converti par mammoth, sans signalement. Le texte des zones de texte peut survivre, pas la mise en page.
- **Numérotation reprise** : une liste Word qui « continue » une liste précédente arrive avec `start`, mais la reprise exacte dépend de ce que Word a sérialisé.
- **Notes de bas de page** : conservées dans `html` via `data-footnotes` / `data-footnote`, mais le schéma Tiptap ne garde pas ces attributs après `setHTML` ; seule la liste finale et les appels `[1]` restent.
- **Styles custom** : un style de paragraphe inconnu remonte en avertissement `mammoth` et devient un `<p>`. Ajoute une règle dans `styleMap` pour le mapper.
- **Google Docs** : les `li` gardent leur `<p>` ; les couleurs et tailles posées par Google sont jetées comme pour Word.
- **Aller-retour export → import** : une liste dans une citation, un `li` multi-paragraphes avec sous-liste et `<ol start>` sont exportés fidèlement pour Word mais dégradés par mammoth à la réimportation. Détail et HTML obtenu dans [Limites connues de l'export](#limites-connues-de-lexport).

## ⚖️ Poids de mammoth et de docx, import dynamique

mammoth pèse environ **660 kB non minifié**, la lib `docx` environ **1,3 MB**. `importDocx` charge mammoth via `await import('mammoth')` au premier appel **en mode `semantic` seulement** (le lecteur stylé, défaut depuis la 0.6, ne s'en sert pas : `jszip` et le `DOMParser` suffisent, un import par défaut ne télécharge donc plus mammoth) et `exportDocx` fait de même pour `docx`, gabarit ou pas : ni l'un ni l'autre n'entre dans le bundle initial si ton bundler suit le code-splitting (esbuild, Vite, Angular CLI le font). Pour aller plus loin, importe aussi le paquet à la demande :

```ts
async function loadDocx(file: File): Promise<string> {
  const { importDocx } = await import('@aster-editor/word');
  return (await importDocx(file)).html;
}
```

`wordPasteTransformer`, `normalizeWordHtml`, `normalizeGoogleDocsHtml`, `jsonToHtml`, `downloadDocx` et `compareDocx` n'ont **aucune dépendance** à mammoth ni à `docx` : les importer statiquement ne coûte que leur propre code (et `jszip` pour le comparateur). Sur `ng serve`, le tout premier `importDocx` ou `exportDocx` d'une session peut recharger la page : l'optimiseur de dépendances de Vite découvre mammoth ou `docx` à ce moment-là (voir le [guide d'intégration](../../docs/GUIDE_INTEGRATION.md)).
