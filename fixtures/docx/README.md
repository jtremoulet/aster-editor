# 📎 Fixtures .docx

> Documents de référence pour tester l'import Word, l'export dans le gabarit et le rapport de fidélité. 01-06 et 08-20 ont un HTML attendu **stylé** dans `expected/` (sortie du chemin par défaut d'`importDocx`, `fidelity: 'styled'` depuis la 0.6) ; 01-03 et 08-10 ont en plus leur HTML **sémantique** (mammoth, `fidelity: 'semantic'`, comportement 0.4.x) dans `expected/semantic/` ; 04-07 sont des documents réalistes couverts par `import-all-fixtures.spec.ts` (la 07, fixture de charge, n'a pas d'attendu) ; 11-20 et les documents client ont un score de fidélité attendu.

## 📥 Déposer un document réel

Deux cas :

- **Document publiable** (anonymisé, aucune donnée personnelle, aucun nom de client, aucun logo propriétaire) : le copier ici sous le nom `NN-description.docx`, puis ajouter une ligne au tableau avec sa provenance et ce qu'il contient. Le test `import-all-fixtures.spec.ts` du paquet `word` l'importera automatiquement et vérifiera qu'il ne produit ni rejet ni avertissement d'erreur.
- **Document client non publiable** : le déposer dans `client/`, **ignoré par git** (`.gitignore` : « documents clients déposés pour les tests de fidélité, jamais publiés »). Rien n'est commité, rien n'apparaît dans le dépôt ; les tests qui le lisent (`client-doc.spec.ts`, `reader/blocks-fixtures.spec.ts`, `compare/compare-fixtures.spec.ts`) sont en `describe.skipIf(!existsSync(…))` et s'activent dès qu'il est là. Pour mesurer sa fidélité : `npm run fidelity -- fixtures/docx/client/mon-document.docx`. Un seul document réel a changé la qualité du résultat de la session 3 : c'est la source la plus utile.

## 🔁 Régénérer les fixtures synthétiques

```bash
npm run fixtures
```

Les fichiers `01` à `03` viennent de `scripts/generate-fixtures.ts`, `04` à `07` de `scripts/generate-fixtures-extra.ts`, `08` à `10` de `scripts/generate-fixtures-variables.ts`, `11` à `17` de `scripts/generate-fixtures-layout.ts`, `18` et `19` de `scripts/generate-fixtures-sections.ts` (`node scripts/generate-fixtures-sections.ts` pour ces deux-là seules), `20` de `scripts/generate-fixtures-fields.ts` (session 5, L53 : `node scripts/generate-fixtures-fields.ts` pour elle seule ; branché en fin du script `fixtures` du `package.json` racine par l'orchestrateur). Les six scripts sont reproductibles (seul `docProps/core.xml` change d'un run à l'autre).

### 📐 Ce que le score mesure, et ses limites

Le score est la **moyenne pondérée par groupe** des taux `conservé / total` (`tally.ts` : texte 3, style et format de paragraphe 2, format de run 2, tableaux 2, en-têtes/pieds 2, sections 2, parties du paquet 2, listes, images et notes 1). Un groupe sans occurrence ne compte pas. Conséquences à connaître avant de lire un chiffre :

- **Un document sans texte score encore ≈ 0,6.** Fixture 13 avec tout le texte effacé (`<w:t/>` partout) → 0,615 : les parties du paquet, les sections, les styles de paragraphe et l'alignement restent « conservés ». Mise en forme retirée (`w:rPr` et `w:pPr` supprimés) → 0,709.
- **Un corps vide score ≈ 0,3** (`<w:body><w:p/><w:sectPr/></w:body>`) : 0,364 pour 11 et 17, 0,308 pour 12, 13 et 14, 0,25 pour 15, 0,167 pour 16 — `package-part`, `section` et `header-footer` valent 1 et pèsent 6 sur 15 à 20.
- Le score ne dit donc pas, seul, qu'un document est resté lisible : c'est pourquoi le script rend son verdict sur le score **et** sur `paragraph.text` ≥ seuil (R30-10), et que les tests assertent la part de texte conservée plutôt qu'un plancher de score.
- Ce que le score ne compare pas : habillage et position des images, points de suite des taquets (et taquets d'un paragraphe sans tabulation), `w:pPr` des `w:tblStylePr` (alignement ou espacement conditionnels, que le lecteur ignore aussi), commentaires, signets, texte supprimé en révision (voir les notes en bas de chaque rapport). Les styles conditionnels de tableau sont comparés depuis L46 (résolus par cellule comme le lecteur, drapeaux `w:tblLook` en `table.conditional`).
- Alignement des blocs : préfixe et suffixe communs, puis LCS sur le texte canonique ; au-delà d'un million de cellules, ancrage sur les paragraphes au texte unique (patience diff, R30-06). Entre deux blocs appariés, un trou de même taille des deux côtés est apparié par position (bloc modifié) ; un bloc retiré plus un bloc ajouté coûtent plus qu'un bloc retiré (R30-09).
- Champs de fusion : comparés par **nom brut** (`MERGEFIELD "Nom Client"`, `nom_client` et `"NOM CLIENT"` sont trois champs distincts, R30-04) ; un `{{nom}}` écrit en clair, ce qu'Aster produit à l'import, vaut le champ dont le nom normalisé est le même.

Pour voir le détail d'une fixture : `npm run fidelity -- fixtures/docx/14-tableaux-riches.docx --keep /tmp/14.docx` (rapport Markdown sur la sortie standard, `--out` pour l'écrire, `--no-template` pour l'export neuf, `--threshold` pour le verdict, borné à [0, 1]). Codes de sortie : 0 OK (score **et** texte au seuil), 1 KO, 2 usage, 3 erreur d'exécution (fichier introuvable, document illisible, dossier de sortie absent), message sans pile (R30-11).

- Démo Angular : `npm run demo`, page **Import Word**, glisser un fichier ; le sélecteur `styled` / `semantic` change le chemin de lecture (`styled` = défaut de la lib depuis la 0.6, le composant ne force plus rien) et la mise en page lue s'affiche (format, orientation, marges).
